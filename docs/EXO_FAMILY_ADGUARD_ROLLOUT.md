# Shared Family AdGuard Rollout

This document is public-safe. It describes device roles and gates only; it does
not include private hostnames, addresses, credentials, pairing material or live
configuration values.

## Authority

- Boot authority starts at `BOOT_MANIFEST.yaml`.
- Home Edge execution must use the canonical node `home-edge-01`.
- Runtime operations must go through `/usr/local/bin/home_edge_exec --server`
  with request id, idempotency key, audit receipt, Registry, State DB and
  MemoryGate records.
- This rollout adds only a policy and read-only preflight layer. It does not add
  a DNS resolver, packet parser, second executor or control plane.
- No stage may use root gate override, insecure `0.0.0.0`/WAN binding, router
  mutation, DHCP mutation, firewall mutation, Tailscale Admin mutation, AdGuard
  restart or phone VPN mutation from this PR.

## Outcome Model

Every operation reports these outcomes separately:

- `sent`: request was submitted to the registered executor.
- `accepted`: registered executor accepted the request.
- `applied`: an approved mutation changed the intended state.
- `physically_verified`: a separate device observation verified the state.
- `observed`: read-only evidence was collected.

No runtime switch is made by this implementation.

## Stage A: Read-Only Preflight

Stage A is nonmutating. It checks existing LAN primary/secondary AdGuard
coverage, router DHCP DNS posture, outbound DNS enforcement, IPv6 RA/RDNSS,
local static/manual DNS exceptions, failover, Tailscale status and per-client
resolver attestation.

The preflight packet is generated by:

```bash
python3 scripts/family_dns_preflight.py
```

The packet contains public-safe Home Edge exec request templates only. They are
not signed or sent by the script.

## Stage B: Proposed Tailnet-Only Secondary Bind

After Stage A clears, a future approved mutation may bind the existing
secondary AdGuard DNS service to the Home Edge tailnet address only. The design
requires backup, service-order safeguards, restart safeguards, a live Redmi
probe, normal LAN DNS probe and rollback if listener checks or DNS checks fail.

The proposed operation is design-only in this PR:
`family_dns_bind_secondary_adguard_tailnet_v1`.

It must not bind new public interfaces, WAN interfaces, `0.0.0.0` or `::`.

## Stage C: Proposed Tailscale DNS

Only after tailnet-only DNS access is physically verified, a future approved
control may set the tailnet global nameserver to the approved private DNS server
role and enable Override DNS. Current DNS settings must be verified for Home
Edge, Redmi, Windows and every enrolled family client rather than assumed.
MagicDNS, all-client reachability and rollback gates are mandatory.

Tailscale tailnet settings may change only through a registered approved
control, never through this preflight.

## Stage D: Pilot and Family Rollout

The pilot order is Redmi first with DNS left off until readiness is proven,
then family Samsung/iPhone clients only after their own consent and opt-in
tailnet enrollment, then LAN roles such as TV, tablet, Home Assistant, printer,
Nest, Windows and any other observed clients.

IPv6 RA/RDNSS bypass, local manual DNS, public or private DoH/DoT app bypass
and captive portal failure cases must be reported honestly. This rollout does
not use MITM or certificate installation. Existing plain DNS is preferred on
the home LAN; away devices should use the existing encrypted Tailscale tunnel
to the private DNS server. Android system DoT certificate setup is not required
for that tunnel path.

DNS-only filtering cannot guarantee ad blocking in native YouTube or in apps
that serve ads from the same hostnames as wanted content. UI expectations must
say that plainly.
