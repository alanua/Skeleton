# Threat Model

Skeleton coordinates AI-assisted work across repositories, runtimes, private state, and edge systems. The primary security assumption is that **model output is untrusted input** and must not become authority merely because it is plausible or generated by a capable model.

This document describes the main trust boundaries and failure modes. It is not a claim of formal verification.

## Security objectives

Skeleton aims to preserve:

1. **Human authority** over merge, deployment, credentials, network/firmware changes, destructive operations, and physical-device actions.
2. **Repository integrity** by binding sensitive actions to explicit repositories, targets, reviewed revisions, and allowlisted operation types.
3. **Private-state separation** so public repositories and audit artifacts do not absorb credentials, personal data, private paths, or device topology.
4. **Execution containment** through registered runners/executors rather than arbitrary model-selected command paths.
5. **Recoverability** through rollback, failure history, leases/retries, and safe re-entry points.
6. **Verifiability** by separating command delivery from observed postconditions.

## Authority ladder

    Human decision / explicit repository policy
            >
    Canonical private runtime state
            >
    Derived indexes, caches, summaries, or projections
            >
    LLM inference

Lower-authority sources may assist reasoning but must not silently override higher-authority sources.

## Trust boundaries

### 1. Model output -> Skeleton control plane

Threats:

- hallucinated repository state;
- invented commands or paths;
- prompt injection from issues, files, logs, or external content;
- attempts to broaden a task beyond its declared scope.

Controls:

- manifest-driven boot and declared source order;
- explicit project and provider routing;
- allowlisted operations;
- exact-state validation;
- task/workspace isolation;
- human approval for sensitive transitions.

### 2. GitHub issue / PR content -> Runner

Threats:

- malicious issue text;
- repository confusion;
- stale reviewed revisions;
- branch/worktree contamination;
- cross-repository authority escalation.

Controls:

- registered project routes in PROJECT_TREE.yaml;
- bounded issue workspaces;
- explicit target repository metadata;
- clean-workspace checks;
- expected-head SHA checks for protected actions;
- separate runtime-maintenance paths.

### 3. Action proposal -> protected mutation

Threats:

- approving a different action than the one reviewed;
- PR changing after review;
- path traversal or unexpected file scope;
- implicit approval inferred from conversational context.

Controls:

- ActionGate-style requests bind action type, repository, PR, expected head SHA, expected files, and explicit approval;
- non-allowlisted action types fail closed;
- future/live mutation routes must preserve those bindings rather than treating approval as a generic token.

### 4. Public repository -> private runtime

Threats:

- leaking credentials or private topology into public artifacts;
- using public data as if it were canonical private state;
- exposing personal documents or runtime databases;
- logging raw environment data.

Controls:

- explicit public/private routing;
- audit payload validation;
- rejection of obvious secrets, private paths, Drive references, and .env-like content;
- opaque private-reference stubs instead of raw locators;
- secrets remain in protected runtime/secrets systems.

### 5. Runner / control plane -> Home Edge

Threats:

- bypassing the registered executor;
- running as the wrong user;
- confusing command acceptance with physical success;
- replaying a mutation;
- losing rollback state.

Controls:

- registered execution node and operation metadata;
- execution lanes and approval references;
- idempotency keys;
- bounded timeout/output;
- rollback definitions;
- independent post-condition checks;
- durable operation/audit evidence.

### 6. Cross-repository dependencies

Threats:

- stale compatibility copies;
- source-of-truth ambiguity;
- dependency revision drift;
- hidden fallback to obsolete implementation.

Controls:

- explicit repository ownership;
- exact source-revision contracts;
- CI contract checks;
- fail-closed behavior when a required external component is unavailable or broken;
- removal of duplicate implementation after separation is validated.

## High-value attack surfaces

The most security-sensitive areas include:

- executor and approval bypass;
- GitHub workflow and token permissions;
- repository/target confusion;
- child-process environment and credential inheritance;
- dependency/source provenance;
- Android/Home Edge boundary handling;
- audit-record tampering;
- unsafe fallback between model/provider/runtime routes;
- post-condition spoofing;
- firmware/network/device operations.

These are the areas where deeper automated security review can provide the highest leverage.

## Security-testing philosophy

A green command exit code is not enough for security-sensitive workflows.

Skeleton distinguishes:

    requested -> sent -> accepted -> applied -> independently verified

Where rollback exists, rollback evidence is also part of the success boundary.

Tests should prefer literal contract assertions around authority, allowed values, exact revisions, and failure behavior. When a dependency or authority source is unavailable, the safer default is to block rather than silently degrade into a broader permission path.

## AI-assisted maintenance boundary

AI tools may:

- inspect code and architecture;
- draft focused patches;
- propose tests;
- summarize issues;
- assist review;
- generate bounded task packets.

They do not automatically gain authority to:

- merge or deploy;
- read or move secrets;
- alter production network/firmware policy;
- bypass approval gates;
- rewrite canonical private state;
- operate physical devices outside registered execution paths.

## Reporting

See [../SECURITY.md](../SECURITY.md) for vulnerability-reporting guidance. Public reports must not include credentials, private topology, personal data, or a working exploit against systems the reporter does not own or have permission to assess.
